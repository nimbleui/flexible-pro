## 项目定位

企业级低代码插件平台：**应用插件内核 + 画布微内核 + 声明式贡献**。

- 一个零依赖的插件内核（`@lc/kernel`，10 个源文件）提供上下文树、服务注入、依赖驱动生命周期与副作用自动回收。
- 一个纯算法的画布微内核（`@lc/canvas`，12 个源文件）提供视口、场景、命中、交互分发、覆盖层与吸附。
- 缩放、平移、选择、拖拽、缩放尺寸、旋转、吸附、网格、辅助线、标尺、小地图、对齐、右键菜单、编辑命令、物料拖入 —— **15 项画布能力全部是插件**，宿主与预设不认识任何一个具体能力。
- 插件在 `manifest.contributes` 里声明纯数据贡献，宿主只消费贡献表；入口模块只在被真正用到时才 `import()`（面板按激活事件、物料按文档出现、能力按 CanvasRealm）。

## 阅读路径

**第一次接触平台** → 01 → 02 → 03，再按需深入 04/06。

**要写一个插件** → 10（配方）→ 05（能声明什么）→ 08（现有插件的实际写法）→ 06 或 07（要用哪个 API）。

**排查运行时行为** → 02（哪一跳断了）→ 04（生命周期/依赖为何 pending）→ 06（交互分发顺序）→ 07（服务不变量）。

**评审架构决策** → 03（取舍与被拒方案）→ 01（依赖方向是否被破坏）。

**要拆微前端 / 加一个远程模块** → 12（边界与契约）→ 09（`@lc/vue` 的注入键与外壳）→ 01（两个应用的依赖边）。

**要评估或实现版本控制** → 13（已落地事实、剩余提案与分阶段计划）→ 05（版本服务契约 / `SchemaPatch` / `migrateDocument` / 保留服务名现状）→ 07（document 与 history 的写入链）→ 08（版本面板插件）→ 09（宿主的发布与资产 store、rail 入口）。

## 维护约定

1. **改动即同步**：修改 `PluginDefinition`、`PluginManifest`、贡献点、保留服务名单、`SLOT`、`LayerBand`、事件表或视口常量时，必须同步本目录对应文档；这几处是平台的稳定契约面。
2. **只写已验证事实**：文档中的行为描述必须能在源码里指出出处；无法从代码确认的设计意图标注为「现状」而不写成「规范」。
3. **不描述未实现能力**：`iframe`/`worker` 执行位置、`when` 条件求值、设置持久化、控制面签发授权等在设计稿中存在但代码未实现的能力，只允许出现在 10 号文档的「已知边界」一节。**唯一例外**是标了「提案，未实现」的方案文档（当前为 13）：它必须逐条区分**现状**（可源码核对，带 `文件:行号`）与 **`[提案]`**（代码里还不存在），并自己声明基线 commit；任一阶段落地后，该阶段的事实要回填到 05/07/08/09 对应章节，方案文档只保留仍未实现的部分。
4. **行号会漂移**：引用优先给出**符号名**（如 `PluginRuntime.activate`），行号仅作定位辅助；重命名符号时同步改文档。
