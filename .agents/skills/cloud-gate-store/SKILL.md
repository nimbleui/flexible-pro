# Enterprise Frontend Engineering

## 技能目标

本 Skill 用于指导 Agent 在企业级前端项目中进行稳定、可维护、可扩展的生产级开发。

目标不是创建最复杂的架构，而是在保持现有项目约束的前提下，用最小且清晰的设计完成真实需求，并让代码能够长期演进。

## 适用范围

当任务涉及以下场景时使用本 Skill：

- Vue 3 组件、Composition API、Composables 开发。
- TypeScript 模块、公共类型、API 设计。
- 基础组件与前端基础设施设计，如 Floating、Tooltip、Popover、Dropdown。
- 插件 / Middleware 等可扩展机制设计。
- pnpm workspace、Monorepo、Vite、Module Federation 相关工程开发。
- 架构重构、Bug 修复、性能优化、Code Review。
- ESLint、Prettier、cspell、commitlint、lint-staged、Vitest 等工程质量治理。

## 不适用范围

以下任务默认不使用本 Skill，除非它们是当前前端工程任务的一部分：

- 纯 Node.js 后端服务开发。
- React、Angular、Svelte 等非 Vue 技术栈项目。
- 与前端工程无关的纯算法题、数据分析或运维任务。
- 与当前仓库无关的通用技术问答。

## 核心原则

### 1. 先理解，再修改

修改代码前，先理解相关目录、模块入口、类型、已有工具、Composables、组件、测试和依赖关系，确认是否已有能力可以复用，并明确修改影响范围。

优先顺序：

```text
现有设计
  ↓
现有约束
  ↓
现有扩展点
  ↓
需求真正需要改变的部分
  ↓
最小修改方案
```

不要因为出现新需求就立即创建一套新系统。

### 2. 正确性优先于抽象

设计和实现的优先级：

```text
正确性
  ↓
现有项目约定
  ↓
简单性
  ↓
可维护性
  ↓
可读性
  ↓
可测试性
  ↓
扩展性
  ↓
性能
  ↓
代码复用
  ↓
设计模式与技巧
```

不为了展示设计模式、TypeScript 技巧或“高度抽象”增加无意义复杂度。

### 3. 使用最小可行设计

优先选择：

```text
简单数据结构
+
清晰函数
+
明确职责
+
有限扩展点
```

如果普通函数可以解决问题，不增加 class；如果数组可以解决问题，不增加 Registry；如果明确接口可以解决问题，不增加多层抽象。

新增抽象前至少判断：

1. 是否存在两个或以上真实使用场景。
2. 抽象后是否明显更容易理解和维护。
3. 删除该抽象是否会让实现明显变差。

不能回答清楚时，不增加抽象。

### 4. 保持边界稳定

- 公共 API 必须稳定、明确、可理解。
- 修改公共 API 前判断是否属于 Breaking Change。
- 优先扩展现有实现，其次小范围重构，再考虑抽取公共能力；重写模块应是最后选择。
- Core 负责能力，Framework Adapter 负责框架适配，Component 负责 UI。
- 公共模块应允许内部实现调整，而不迫使消费者依赖内部细节。

### 5. 类型系统不是绕过目标

TypeScript 应帮助表达真实约束，而不是被断言、`any`、`@ts-ignore` 或 `as unknown as` 绕过。

公共 API、公共类型和关键数据结构必须具有清晰的类型语义。

### 6. 解释“为什么”

重要设计和公共代码的注释优先解释：

- 为什么这样设计。
- 为什么需要这个状态、类型或抽象。
- 生命周期、性能或边界条件是什么。
- 为什么没有采用更简单的方案。

不要用注释重复代码表面行为，也不要用注释掩盖错误设计。

### 7. 只声明真实验证结果

完成任务后应按照项目实际约定执行必要的质量检查，包括格式化、Lint、Type Check、相关测试和必要的 Build。

具体命令以仓库的 `AGENTS.md`、`package.json`、CI 或现有脚本为准。本 Skill 不硬编码项目级命令。

禁止虚构“已验证通过”。

## 任务决策流程

复杂任务开始前，依次明确：

```text
需求是什么？
  ↓
现有实现是什么？
  ↓
真正的问题在哪里？
  ↓
哪些模块受到影响？
  ↓
现有能力能否复用？
  ↓
是否真的需要新抽象？
  ↓
最小方案是什么？
  ↓
未来扩展点应该保留在哪里？
```

Bug 修复优先遵循：

```text
复现
  ↓
定位 Root Cause
  ↓
设计最小修改
  ↓
修复
  ↓
增加必要的回归测试
  ↓
执行项目实际质量检查
```

重构默认保持行为不变，除非需求明确要求改变行为。

## 渐进式读取规范（强制）

在编写任何代码之前，必须根据当前任务，强制读取对应的参考规范。禁止在未读取对应规范的情况下直接编写代码。

必须遵循以下条件触发规则：

- 如果任务涉及 TypeScript 类型、函数设计、命名、注释 -> 必须读取 `references/typescript.md`
- 如果任务涉及 Vue 组件、Composables、状态 -> 必须读取 `references/vue.md`
- 如果任务涉及公共组件样式、SCSS、Token -> 必须读取 `references/styles.md`
- 如果任务涉及 Monorepo、Package 边界、Module Federation -> 必须读取 `references/architecture.md`
- 如果任务涉及 DOM 测量、滚动、Floating、性能 -> 必须读取 `references/performance.md`
- 如果任务涉及测试、Bug 修复、重构 -> 必须读取 `references/testing.md`

一个任务可能触发多个条件，必须读取所有对应的文件。

## 完成标准

任务完成前确认：

- 需求已真实实现，而不是伪实现或仅覆盖 Happy Path。
- 修改范围与需求相匹配，没有无关重构。
- 没有破坏明确的架构边界和稳定公共 API。
- TypeScript 类型没有被危险断言或忽略指令绕过。
- 新增复杂度具有真实价值。
- 需要的测试和工程检查已按项目实际命令执行，或明确说明无法执行的原因。
- 没有遗留无意义 TODO、隐藏错误或不必要依赖。
- 重要公共 API 和关键设计具备必要说明。

最终输出应清楚说明：本次修改内容、涉及文件、关键设计、设计原因和实际验证结果。

## 最终原则

> 不创建当前不需要的复杂度。

> 不破坏已经稳定的 API。

> 不绕过 TypeScript 和工程质量体系。

> 公共能力必须考虑长期维护成本。

> 抽象应该来自重复出现的真实问题，而不是来自对未来的想象。

> 每增加一层抽象，都必须能够回答：这一层解决了什么真实问题？
